# 《茶游记》小红书版本 · 开发评估

> 评估时间：2026-09-12
> 评估范围：检查当前网页版本代码与已存在的小红书（XHS）构建，判断「小红书版双茶区 MVP」的可复用资产、适配成本、技术风险与开发顺序。
> 评估原则（用户要求）：**只检查与评估，不大规模改代码**。本文件为下一阶段正式开发的依据。

---

## 结论速览（先看这里）

1. **小红书版目前没有真正可用的版本。** `build:xhs` / `xhs.html` / `main-xhs.tsx` 已搭好构建链路，但 `src/app/XhsApp.tsx` 只是一个**未接叙事的线性 demo**（首页 → 选茶 → 制茶 → 结果 → 泡茶 → 一张分享卡），**没有茶区选择、NPC、探索、茶席、漫画、背包、剧情**。它不是用户想要的「轻量化移动版」，需要重做/升级。
2. **网页版本的内容资产复用率极高（估计 85%+ 可直接或轻量复用）。** 游戏逻辑、数据、玩法组件都由一套「core 数据 + Zustand store + region-agnostic 组件」承载，Web 与 XHS 共用同一份代码与数据。
3. **网页版本已经长成「移动竖屏单列」的样子。** `.app` 容器 `max-width: 480px`、`min-height: 100dvh`、带 `safe-area-inset`、场景舞台 `aspect-ratio 390/560`、已设 `touch-action: manipulation` / `overscroll-behavior: none`。所以 XHS 主要不是「把桌面网页改小」，而是「套一个移动外壳 + 收敛少量浏览器 API + 资源瘦身」。
4. **茶区是半数据驱动。** 内容（茶/人/配方/漫画/偶遇/茶席/散步）已数据化；唯独「某地点进场景后先播谁、播完显示什么 UI」的接线写死在 `WebApp.tsx` 的逐茶区分支里。双茶区 MVP 不受影响；扩到 3+ 茶区时再抽象即可。
5. **最大风险不是功能，是平台外壳与资源加载。** 本地存档（localStorage）、返回键、分享、首屏与图片体积，是 XHS 环境特有的工作量。
6. **建议现在开始开发**，采用「**复用 WebApp 全量流程 + platform 外壳**」的轻量路线（不重构），把现有 `XhsApp` 线性 demo 升级为复用完整内容的移动外壳。

## 【2. 当前网页版本可复用资产】

### A 类 · 可直接复用（几乎零改动）

- **制茶玩法**：`features/making/*`（采茶 `PickingStep`、做青、炒揉、焙火、萎凋、揉捻、发酵、烘干、理条、干燥）+ `MakingFlow`，由 `getRecipeFor(teaId)` 按茶类选配方（岩茶/红茶/绿茶三条 `RECIPE`），完全数据驱动。
- **泡茶玩法**：`features/brew/BrewingFlow.tsx`（8 步泡茶）、`TeaStackPicker.tsx`。
- **结果 / 评价**：`features/result/ResultView.tsx`、`core/data/brewEval.ts`、`core/data/zhouBoAdvice.ts`（周伯点评，与底部评价同源 `lastResult`）。
- **茶叶 / 背包 / 茶具数据**：`core/data/teas.ts`、`teaWares.ts`、`souvenirs.ts`；背包状态在 store `player.inventory / teaWareInventory`，含「自制/购买/赠礼」来源、礼物茶可泡不可卖等规则。
- **NPC 与对话**：`core/data/npcs.ts`（NPC 纯数据）、`core/data/dialogues.ts`（`Dialogue[]`，trigger 分 `first/repeat/conditional(flag)`、可 `setsFlags/givesTea/givesTeaWare`，派生条件即时计算不落盘）。
- **茶席**：`core/data/teaseat.ts`（`TEA_SEAT_BY_REGION` 纯数据 + 纯函数判定）、`features/teaseat/TeaSeatView.tsx`（背景→NPC→茶桌→三槽位→玩家分层，z-index 显式）。两茶区已区域化。
- **喝茶**：`gameStore.drinkTea(stackId)`（复用 `consumeOne`，一次真喝扣 1 包）。
- **轻剧情 / 章节衔接**：`core/data/regions.ts` 的线索 `CLUES`、解锁 `isWuyishanExplored`、武夷山→杭州收束逻辑；牛姐彩蛋、梅家坞吟诗、茶联等全部数据 + 状态机驱动。
- **漫画 / 科普**：`core/data/comics.ts` + `features/journal/ComicView.tsx` / `ComicArt.tsx`；手账 `JournalView` / `RegionJournalView` / `SouvenirView`。
- **偶遇 / 区域探索**：`core/data/encounters.ts`（按 `scenes` 权重）、`encounterEngine.ts`（支持 `regions?` 茶区过滤、`requires` 守卫、当日冷却）、`features/encounter/EncounterLayer.tsx`；杭州散步 `core/data/strolls.ts` + `StrollView.tsx`。
- **茶区选择 / 地图（数据驱动，可直接用）**：`features/world/TeaWorldView.tsx`（四宫格卡片，来自 `TEA_WORLD_REGIONS`，按 `unlockFlag` 解锁）、`features/world/MapView.tsx`（按 `currentRegion` 渲染地点，来自 `REGIONS`）。

### B 类 · 可复用但需小红书端适配（外壳 / 交互 / 资源）

- **场景布局 `NpcStage` + `scenes/index.ts`**：场景大图（位图）+ 透明 NPC 立绘 + 底部对话浮层已是「移动竖屏」结构；需确认对话浮层在极小屏不溢出、立绘比例在 XHS 画布内。
- **对话框 `NpcDialog`**：底部浮层样式；需加移动端最大高度 + 内部滚动，避免长对话溢出。
- **点击交互 / 按钮**：`.btn`、`.loc-card` 多为整宽大按钮（触控友好）；但若干 `:hover` 样式（`.stall-card`/`.region-card`/`.tw-menu-item`）在触屏会「粘滞」，建议补 `:active` 触感反馈。
- **茶席**：逻辑可复用；分层场景在移动端需确认各层 z-index 与容器比例（不裁切）。
- **背包 / 茶具收藏 / 手账**：数据可复用；列表在窄屏需确认横向滚动（`ware-cards` 已 `overflow-x:auto`）与卡片密度。
- **页面切换 / 导航**：store 自带 `go/back/navHistory` 历史栈（不依赖浏览器历史）——这对 XHS 是好事，可把「系统返回键」映射到 `back()`。
- **动画**：茶世界叶片飞行、`couplet` 展开等均为 CSS/JS 动画，可复用；首屏与场景切换的加载态需补（见风险）。
- **图片资源**：背景/立绘为 webp，需评估移动端体积（见第 4、7 节）。

### C 类 · 需要重新实现 / 平台适配（小红书特有）

- **页面生命周期 / 首屏**：XHS 容器生命周期（冷启、后台回收、重进）需要接壳层管理；当前 `start` 页 + `loadSave()` 已能续档，但需在外壳层保证「重进不丢进度」。
- **返回逻辑**：系统返回键需映射到 store `back()`（Web 用浏览器返回/按钮；XHS 无浏览器返回，必须自定义）。
- **本地存档**：当前 `core/storage/storage.ts` 用 `localStorage`（key `teaworld.save.v3`），Webview 内可用但**若 XHS 每次开新 webview 会清空**——需确认 XHS 提供的持久化能力，必要时换壳层存储。
- **平台 API / 分享**：XHS 的「截图分享 / 笔记发布 / 唤起客户端」是平台能力；当前 XHS 分享卡只是页面内一张可截图元素，真正的「一键发布到小红书」需平台桥接。
- **资源加载策略**：首屏资源、懒加载、预加载下一场景背景——Web 靠浏览器缓存，XHS 可能需壳层预取。

## 【3. 小红书端需要适配的内容（具体 + 原因）

| 内容 | 现状 | 为什么需适配 |
|---|---|---|
| `XhsApp` 外壳 | 线性 stub，无茶区/NPC/探索/茶席 | 用户要的是「轻量化完整游戏」，不是「做一杯茶分享」；必须升级为复用完整内容的移动外壳 |
| `difficulty` | XHS 已强制 `casual`（铁律：双端差异只走 `params.standard/casual`） | 保持；XHS 默认休闲档，不改玩法数值 |
| 返回键 | Web 用浏览器/按钮；store 有 `back()` | XHS 无浏览器返回，必须壳层把系统返回键接到 `back()`，否则「返回上一页/场景状态」丢失 |
| `window.confirm` / `window.location.reload()` | `MapView` 重开游历用浏览器确认 + 整页刷新 | Webview 里体验差、刷新可能丢 XHS 上下文；改为应用内确认弹窗 + `store.reset()` |
| 存档 | `localStorage` | Webview 若每次新建会清空；需确认 XHS 持久化或加壳层存储桥 |
| 分享 | 页面内分享卡 | 「发到小红书」是平台能力，需壳层桥接（MVP 可先只做「截图/长按保存」） |
| 背景图体积 | 场景背景 15 张，188KB–564KB（合计 ~5.5MB），最大 `workshop.webp` 564KB；NPC 立绘合计 ~6MB | 移动弱网卡首屏/进场景慢；按场景懒加载已存在，可再补移动端降质或预取 |
| `:hover` 粘滞 | 若干卡片 `:hover` | 触屏无 hover，可能「选中态不消失」；补 `:active` 即可 |
| 多层弹窗 | 茶联礼物 / 偶遇层 / Toast / DayIntro 均为 `position:fixed` 覆盖层 | 小屏需明确 z-order 与一键关闭，避免叠层难退 |

## 【4. 当前最大技术风险

1. **平台外壳与生命周期（中高）**：返回键、存档持久化、首屏、后台回收——这些在 Web 由浏览器兜底，XHS 必须自管。若 XHS 用「每次新建 webview」，`localStorage` 会丢，玩家进度无法保留。**这是上线前必须验证的第一风险。**
2. **资源加载与首屏体积（中）**：背景 ~5.5MB + 立绘 ~6MB（全量），弱网首屏慢。按场景懒加载已存在，但 XHS 需明确预取/降质策略，否则进场景白屏或卡顿。
3. **场景接线写死（中，仅影响扩区）**：`WebApp.tsx` 逐茶区 `if (scene === 'hz-teahouse')` 分支承载「地点叙事流」。双茶区 MVP 无碍；扩 3+ 茶区时每区要加分支 + 加 `Scene` 联合类型成员，易漂移。**MVP 阶段不建议改，扩区前再抽成「地点 UI 配置」。**
4. **`window.confirm` / `reload` 的 Web 依赖（低中）**：两处浏览器 API，XHS 体验差但能跑；建议小改替换（见第 3、7 节）。
5. **无平台开关导致的「双端漂移」风险（低，靠纪律）**：铁律要求双端差异只走 `platform`/难度参数，禁止散落 `if (isXhs)`。若后续有人在组件里直接判 `isXhs`，会破坏复用。**风险可控，靠代码评审 + 单一外壳组件约束。**

## 【5. 双茶区 MVP 建议

### 范围合理性
用户给的 MVP 流程（茶区选择 → 进入茶区 → 探索/NPC → 制茶 → 泡茶 → 茶席/喝茶 → 评价/收藏）**合理且可行**，因为网页版这套流程已全数据化、且已长成移动竖屏。

### 必须保留（直接复用 Web 内容）
- 茶区选择（`TeaWorldView`，武夷山已解锁、杭州按 flag 解锁、福州/潮州留锁）
- 茶区地图（`MapView`）
- NPC 对话 + 轻剧情（`NpcDialog` + `dialogues.ts`）
- 制茶 / 泡茶 / 结果评价（`MakingFlow`/`BrewingFlow`/`ResultView`）
- 茶席 + 喝茶（`TeaSeatView` + `drinkTea`）
- 背包 / 茶具 / 手账 / 漫画 / 收藏（数据 + 视图）
- 偶遇 / 区域探索（武夷山山路、杭州梅家坞走走）

### 可以暂时隐藏（MVP 不做，后续加）
- 福州/潮州（仅卡片占位锁定）
- 复杂 RPG 任务树（本来就没有，保持轻量）
- 评分数字（铁律：前台不显示评分数字，品质等级 + 自然语言 + 茶钱）
- 熟练度数值（只显示 初学/入门/熟手/老练）

### 可以在小红书端简化
- 开场 `intro`/日推 `DayIntro`：保留但可更轻（小红书节奏快）
- 茶世界叶片飞行等动画：保留但缩短
- 茶联礼物、明信片等「收藏向」交互：保留，但步骤可压缩

### 明显过重、建议推迟
- 「一键发布到小红书笔记」平台桥接：MVP 先做「截图/长按保存」即可
- 新茶区（潮州/福州）：本期不做
- 与 Web 的云同步：不做（XHS 本地存档即可）

## 【6. 茶区数据结构评估

### 当前是否适合持续增加茶区？——「内容已就绪，接线待抽象」

**已数据驱动（加茶区主要加数据）：**
- `core/data/regions.ts`：`REGIONS`（每区 `locations[]{id,name,npcIds,scene,locked}`）+ `regionLocationScene()` + 解锁/探索/线索函数。
- `core/data/teaRegions.ts`：`TEA_WORLD_REGIONS` 卡片（含 `unlockFlag`/`regionId`），加茶区只需加一项。
- `core/data/teas.ts`：每茶 `regionId` + `gameProfile` + `category`，配方由 `getRecipeFor` 按茶类选（岩/红/绿三条；凤凰单丛可复用岩茶线）。
- `core/data/npcs.ts`、`comics.ts`、`encounters.ts`（支持 `regions?` 过滤）、`strolls.ts`、`teaseat.ts`（`TEA_SEAT_BY_REGION`）、`dialogues.ts`：均为纯数据。
- `scenes/index.ts`：场景 key → `{Component, bg, figure, encounterFigure}`，加茶区加场景条目（背景图 + 立绘站位百分比）即可。

**尚未数据驱动（加茶区需改代码）：**
- `WebApp.tsx`：每茶区的「地点叙事流」是 `if (scene === 'hz-teahouse')` 写死分支（先播玲姨→林姑娘→茶联，再显某 UI）。这是当前**离「纯数据加茶区」最远的一环**。
- `MapView.tsx`：`REGION_ORDER` 与「去山路上逛逛 / 去梅家坞走走」按钮按 `isWuyi` 硬编码；扩区需加分支或抽成 `region.explore`。
- `gameStore.ts`：`Scene` 联合类型需为新区加成员（如 `cz-teahouse`）。

### 理想结构距离
- **双茶区 MVP：已足够。** 武夷山 + 杭州全部就绪，不需为「数据驱动」做任何重构。
- **3+ 茶区：建议先抽一个 `REGION_LOCATION_UI` 配置**（每地点 = 依次播哪些 NPC 对话 + 播完显示什么动作/UI），让 `WebApp` 的逐区分支变成「读配置渲染」。这是唯一值得优先调整的地方，但**本期不必做**（用户明确要求暂不为了数据驱动大规模重构）。
- **可直接复用的抽象雏形已存在**：`regionLocationScene()`、`TEA_SEAT_BY_REGION`、`strolls` 事件池、`encounters` 的 `regions?` 过滤，都是「茶区配置」的好范本。

### 新增一个茶区（如潮州）当前改码量（估算）
数据：+1 `REGIONS` 项、+场景条目、+茶、+NPC、+漫画、+偶遇/散步(可选)、+茶席配置、+对话。
代码：`WebApp.tsx` +1~2 个场景分支（约 30–60 行）、`MapView` 加 `REGION_ORDER` 项、`Scene` 联合 +1~2 成员。
**结论：成本有界、可控；不是「到处改业务代码」。**

## 【8. 推荐开发顺序（P0 / P1 / P2）

### P0（MVP 必须，先做的「最小可用 XHS 外壳」）
1. **升级 `XhsApp` 为「复用 WebApp 全量流程的移动外壳」**：`main-xhs.tsx` 仍渲染一个 `App`，但传入 `platform='xhs'`；默认 `difficulty='casual'`；复用 `WebApp` 全部场景与内容（茶区选择→地图→探索→NPC→制茶→泡茶→茶席→评价→收藏）。**退役现有线性 stub。**
2. **验证存档持久化**：确认 XHS webview 里 `localStorage` 是否跨会话保留；不保留则接壳层存储桥。**（最高风险，先验证）**
3. **系统返回键 → `store.back()`**：自定义移动端返回，保证「返回上一页/场景状态不丢」。
4. **替换 `window.confirm`/`window.location.reload()`**：改为应用内确认 + `store.reset()`（小改，消除 Web 依赖）。
5. **移动端 CSS 皮肤**：在现有 480px 单列基础上，加 `:active` 触感、确认 `NpcDialog` 最大高度、统一弹窗 z-order。

### P1（MVP 体验打磨，P0 之后）
6. 资源瘦身/预取：场景背景移动端降质、按场景懒加载、首屏 loading 态。
7. 分享卡升级：保留「可截图分享」+ 长按保存；平台发布桥接后置。
8. 茶席/背包/手账在窄屏的布局与密度复核。
9. 开场 `intro`/日推 `DayIntro` 在 XHS 节奏下轻量化。

### P2（扩展与平台，MVP 之后）
10. 「一键发布到小红书笔记」平台桥接。
11. 抽象 `REGION_LOCATION_UI` 配置，把 `WebApp` 逐茶区分支变成数据驱动（为 3+ 茶区铺路）。
12. 新茶区（潮州/福州）：加数据 + 少量接线。
13. 与 Web 的云同步（如需要）。

## 【是否建议现在开始开发】——明确结论

**建议现在开始开发。** 理由：

- 网页版本的「内容资产」已高度模块化、数据化、且天然移动竖屏，XHS 不是从零做，而是「套移动外壳 + 复用完整内容」，工作量集中在**外壳与平台适配**，不在玩法重写。
- 构建链路（`build:xhs`/`dev:xhs`）已通，只需把 `XhsApp` 从废弃线性 demo 升级为复用 `WebApp` 流程的移动壳——符合铁律（双端差异只走 `platform`/难度参数，不散落 `isXhs`）。
- 双茶区 MVP 不需要任何「为数据驱动而重构」：武夷山 + 杭州已全部就绪，福州/潮州留锁即可。

### 为什么「现在必须改」的只有两处（其余暂不改）
- **必须改 `XhsApp`**：当前它是空壳 demo，**不改则 XHS 没有任何真实内容**，无法作为 MVP。这是功能正确性，不是优化。
- **建议改 `window.confirm` / `reload`**（小改）：在 Webview 里体验差且刷新可能丢 XHS 上下文；但属体验问题，**不阻塞 MVP 启动**，可与 P0 同步做。
- **不改 `WebApp` 场景接线 / 不做 `REGION_LOCATION_UI` 抽象**：双茶区不需要；现在重构会增加漂移风险与回归成本。**扩到 3+ 茶区前再做**（列入 P2）。

### 唯一需要「先验证再开发」的风险
**XHS 容器是否持久化 `localStorage`**。若每次进小程序都新建 webview 导致存档清空，则玩家进度无法保留——必须在 P0 第一步就验证，必要时改存储桥。不先验证这一点，后续所有内容开发都可能白做。
