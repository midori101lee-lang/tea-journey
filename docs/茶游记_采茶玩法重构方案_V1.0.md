## 2. 新玩法核心逻辑

```
进入茶园（阿秀在）
  ↓ 阿秀自然引导：今天采开面的
观察茶树枝条上的茶梢（不同成熟状态）
  ↓ 玩家判断：哪一梢「开面合适」
按住茶梢 → 向下轻拖 → 茶梢脱离枝条 → 飞入竹篮
  ↓ 采够一篓（或采满采摘机会）
阿秀观察竹篮 → 评价这一篓鲜叶
  ↓ 进入制茶坊（岩伯）
用「这一篓鲜叶」做一锅茶
```

核心体验：**观察 → 判断 → 采摘 → 收获一篓自己的鲜叶**。
判断依据 = 茶梢形态（芽叶关系 / 叶片大小 / 成熟程度），**颜色只是辅助视觉，不是唯一答案**。

---

## 3. 鲜叶生命周期（本轮鲜叶，非长期背包）

```
茶树（场景）
  ↓ 玩家亲手采摘
🧺 本轮鲜叶（竹篮，仅当前这一锅）
  ↓ 进入制茶，被消耗
🔥 做成一锅茶
  ↓
🍵 成茶 → 进入长期背包（inventory，按 grade 堆叠）
```

- **鲜叶不进 `Player` / 不进 `inventory`**：删除 `freshLeaves` 死字段。
- 本轮鲜叶以**隐藏品质档** `basketQuality: 'good'|'normal'|'rough'` 在内存态暂存（store 非持久字段），`finishMaking` 时清空。
- 玩家长期积累的是：成茶 / 茶叶收藏 / 熟练度 / 茶区进度 / NPC 故事 / 旅行记录 —— 不变。

---

## 4. 「一篓茶」机制

- 屏幕下方竹篮 = 本轮容器，视觉随采摘填充。
- 有限采摘机会 `attemptCount`（默认 12），目标 `basketFull`（默认 8 梢算「采满一篓」）。
- 玩家在机会内**选择**采哪一梢，而非「把所有对的都点完」。
- 阿秀台词：「今天先采这一篓，够做一锅茶了。」

---

## 5. 茶梢判断机制（开面采游戏化）

- 每个茶梢是 `TeaShoot` SVG：**茎 + 叶（1~数片）+ 芽**。
- 编码 `kind`：`'tender'`（太嫩，芽未展/叶过小）`| 'suitable'`（开面合适，一芽二/三叶、叶已展）`| 'over'`（偏老，叶大质硬）`| 'damaged'`（受损/虫咬，状态不佳）。
- **视觉靠形态区分，不靠 3 色**：所有茶梢统一茶绿调，仅叶大小/芽开合/茎粗细变化；可加极轻微色差但绝不作为唯一信号。
- 对应真实：武夷岩茶「开面采」—— 不采单芽，采驻芽小开面/中开面。

---

## 6. 采摘交互

- **按住茶梢 → 向下轻拖 → 脱离 → 飞入竹篮**（ Pointer Events + `setPointerCapture`，复用 `BrewingFlow` 的拖拽范式）。
- 轻量动画（茶梢位移 + 入篮淡入）+ WebAudio 轻「咔」声（项目已有 WebAudio 合成，零音频文件）。
- 不做物理模拟。重点：玩家感觉「摘下来一梢」。
- 误拖（拖太短）回弹，不计入采摘。

## 8. 阿秀反馈（评价这一篓）

采完后 `PickingResult` 轻量展示，阿秀看篮给评价（仅自然语言，无分数）：

| basketQuality | 阿秀台词 |
|---|---|
| good | 「嗯，这一篓叶子挺齐。」 |
| normal | 「有几片稍老了，不过还能做。」 |
| rough | 「这篓叶子有点杂，后面得仔细做。」 |

## 9. 采茶 → 制茶 数据传递

- 采茶输出 `basketQuality`（隐藏档，玩家不可见数值）。
- `MakingFlow` 读取 `basketQuality`，通过 `resolveParams` 对后续步骤（尤其 `zuoqing`/`roasting` 的 `band.widthBase`）做**轻量容错修正**：
  - `good` → 容错 ×1.05
  - `normal` → ×1.0
  - `rough` → ×0.9（判断窗口略窄）
- 保持 `scoring.ts` 现有 `picking` 权重 0.15 + `picking_poor` 故障（已存在的数据传递不加破坏）。
- 玩家只通过「阿秀评价 + 后续制茶手感 + 结果」感受因果，看不到内部数值。

---

## 10. 失败机制（已符合，仅需衔接）

- 制茶失败：`finishMaking` 仍把 fail/普通档成茶压入 `inventory` → 这一篓鲜叶已被用掉、这锅没做好（符合你的十二·失败逻辑）。
- 重挑战：回茶园 → 阿秀 → 再采一篓 → 再做。竹篮每次重新采，自然形成「采茶→制茶→更好」的成长循环。

---

## 11. 重复游玩机制

- 采茶非一次性教程，是制茶成长的一环。
- 熟练度（`proficiency`）已存在，采茶表现经 `basketQuality` 轻量影响制茶容错 → 第二次采更仔细 → 制茶更稳 → 第三次更好。

## 12. 武夷山开面采游戏化方案

- `PICKING_CONFIG`（游戏参数，禁入知识系统）：
  ```ts
  interface PickingConfig {
    method: 'open-leaf';      // 开面采
    attemptCount: 12;         // 采摘机会
    basketFull: 8;            // 采满几梢算一篓
    tolerance: { good: 1.05; normal: 1.0; rough: 0.9 };
    feedback: { good: '...'; normal: '...'; rough: '...' };
  }
  ```
- 茶梢形态分布：约 55% suitable / 25% tender / 15% over / 5% damaged（casual 档提高 suitable 比例）。

## 19. 验收标准（你的原话）

> 玩家玩完采茶以后，应该能说：「刚才那一篓茶是我自己采的。」
> 而不是：「我刚刚点了十几个绿色叶子。」

> 玩家进入制茶以后，应该感觉自己是在处理「刚刚亲手采下来的这一篓茶」。

最终链路：🌱 茶树 → 🧺 我采的一篓鲜叶 → 🔥 我做的一锅茶 → 🍵 我泡的一杯茶 → 🗺️ 我在这座茶山留下的一段经历。

## ⚠️ 一个需你拍板的设计分叉

**采茶在架构里的落点（影响是否动 `recipe.steps`）：**

- **方案 A（推荐，最低风险）**：保留 `recipe.steps = ['picking','daoqing','zuoqing','chao-rou','roasting']` 五步不变（不破「五道制茶工序基本结构」铁律）。把 `PickingStep` 重写为沉浸式茶园场景（含阿秀+竹篮），作为**制茶第一步**渲染；其输出 `basketQuality` 被后续四步消耗。视觉上采茶显示茶园、后四步显示制茶坊。
- **方案 B（叙事更干净）**：采茶移出 `recipe.steps`，改为**茶园场景的独立活动**，`recipe.steps` 减为 4 步加工（倒青→焙火）；`basketQuality` 存内存态、进制茶坊时带入。代价：动了「五步结构」的字面定义。

两者都实现你的核心目标；差异仅在「采茶是否仍叫一道制茶工序」。请确认走 A 还是 B，我再进入实现。
